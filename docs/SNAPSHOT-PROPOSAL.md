# ข้อเสนอเรื่องส่งภาพ snapshot (สำหรับทีม AI)

> เขียน 2026-08-28 · ต่อจาก `docs/PUBLISHING-GUIDE.md` ซึ่งเป็นสัญญาที่ใช้อยู่ตอนนี้
> ไฟล์นี้เป็น **ข้อเสนอ ยังไม่ใช่ข้อสรุป** — เขียนมาให้ค้านได้

## สรุปสั้น

ทราบว่าแผนคือส่ง snapshot มาเป็น **base64 ผ่าน MQTT** — เห็นด้วยกับเป้าหมาย (มีภาพไว้ดูย้อนหลังสำคัญมาก
โดยเฉพาะตอนอ่านไม่ออก) แต่ **วิธีส่งจะทำให้ SD card ของ Pi 5 เต็มเร็วมาก** และไปเบียดกับข้อมูลค่าที่อ่านได้

ขอเสนอเปลี่ยน 3 อย่าง:

| | เดิม | เสนอ |
|---|---|---|
| ช่องทาง | base64 ใน MQTT | **HTTP POST ไบต์ดิบ** (ไม่ต้อง encode) |
| ความถี่ | ทุกเฟรม | **เฉพาะตอน `quality != OK` หรือค่าผิดปกติ** |
| เพดาน | ไม่มี | **ไม่เกิน 1 ภาพ/นาที/จุด** |

---

## 1. ทำไม base64 ทุกเฟรมไม่รอด

Pi 5 ที่รับข้อมูลบูตจาก **SD card เหลือพื้นที่ ~19 GB** และต้องเก็บทั้ง DB, ระบบปฏิบัติการ และภาพ

สูตรคิดเร็ว:

```
ขนาดต่อเฟรม = ขนาด JPEG × 1.33     (base64 บวก ~33%)
ปริมาณต่อวัน = ขนาดต่อเฟรม × อัตราส่ง × 86400
```

สมมติ JPEG 640×480 คุณภาพ 80 ≈ **40 KB** → base64 = 53 KB

| แผน | ปริมาณ/วัน | SD 19GB อยู่ได้ |
|---|---|---|
| ทุกเฟรม ที่อัตราปัจจุบัน (~0.29 เฟรม/วิ) | ~1.3 GB | **14 วัน** |
| ทุกเฟรม ที่อัตราที่เคยวัดได้ (26 เฟรม/วิ) | ~119 GB | **4 ชั่วโมง** |
| เฉพาะตอน `UNREADABLE` (ปัจจุบัน 47% ของเฟรม) | ~600 MB | 30 วัน |
| เฉพาะ `UNREADABLE` + เพดาน 1 ภาพ/นาที/จุด | **~72 MB** | สบาย ๆ |

> 🙏 **ช่วยวัดขนาดไฟล์จริงมาให้หน่อย** — เลข 40 KB ข้างบนเป็นการประมาณ
> ```bash
> ls -lh <ไฟล์ snapshot ที่เซฟไว้>
> ```
> ได้ตัวเลขจริงแล้วคำนวณใหม่ได้แม่นขึ้น ถ้าภาพเล็กกว่านี้มากสถานการณ์อาจต่างไป

## 2. จุดที่มองไม่เห็นแต่เจ็บกว่า — broker เขียน SD ซ้ำอีกรอบ

Mosquitto ฝั่งเราเปิด `persistence` ไว้ ซึ่งจำเป็นสำหรับ QoS 1 (ข้อความไม่หายตอน service restart)
ผลข้างเคียงคือ **ทุกข้อความถูกเขียนลง SD หนึ่งรอบก่อน** แล้วเราค่อยเขียนข้อมูลลง Postgres อีกรอบ

ส่งภาพผ่าน MQTT จึงเท่ากับ **เขียน SD ~2 เท่าของขนาดภาพ** ทั้งที่ SD คือชิ้นส่วนที่พังง่ายที่สุดของเครื่องนี้
(เขียนบ่อย ๆ ทำให้อายุสั้นลง และไฟดับตอนกำลังเขียนทำให้ข้อมูลเสียได้)

MQTT ออกแบบมาสำหรับ **ข้อความเล็ก ๆ ถี่ ๆ** ไม่ใช่ก้อนข้อมูลใหญ่ — ส่วน HTTP ออกแบบมาสำหรับกรณีหลังพอดี

## 3. ข้อเสนอ: ส่งภาพผ่าน HTTP POST

### ปลายทาง

```
POST http://smsn-pi-office-01.local:3000/api/frames/<frame_id>/snapshot
Content-Type: image/jpeg
body: ไบต์ดิบของ JPEG  (ไม่ต้อง base64)
```

`frame_id` คือตัวเดียวกับที่ส่งใน `meter_frame` อยู่แล้ว — เป็นกุญแจเชื่อมภาพกับค่าที่อ่านได้
ไม่ต้องเพิ่มฟิลด์ใหม่ในสัญญา MQTT เลย

**ข้อดีที่ได้ทันที**
- ไม่ต้อง base64 → **ประหยัด 33%**
- ไม่ผ่าน persistence ของ broker → SD เขียนน้อยลงครึ่งหนึ่ง
- ถ้าเครือข่ายช้าหรือฝั่งเรารับไม่ทัน HTTP จะช้าลงเอง (backpressure) ไม่ท่วมคิวของ broker
- ฝั่งเราจำกัดขนาด/ปฏิเสธได้ และตอบกลับบอกเหตุผลได้

### โค้ดฝั่ง edge

```python
import requests

SNAPSHOT_URL = "http://smsn-pi-office-01.local:3000/api/frames/{frame_id}/snapshot"

# จำกัด 1 ภาพ/นาที/จุด — ภาพที่อ่านไม่ออกติดกัน 100 เฟรมหน้าตาเหมือนกันหมด
_last_sent = {}
SNAPSHOT_MIN_INTERVAL = 60  # วินาที


def maybe_send_snapshot(frame_id: str, point_id: str, quality: str, jpeg_bytes: bytes) -> None:
    """ส่งภาพเฉพาะตอนมีเหตุ — ภาพตอนอ่านได้ปกติแทบไม่มีใครเปิดดู"""
    if quality == "OK":
        return

    now = time.time()
    if now - _last_sent.get(point_id, 0) < SNAPSHOT_MIN_INTERVAL:
        return
    _last_sent[point_id] = now

    try:
        requests.post(
            SNAPSHOT_URL.format(frame_id=frame_id),
            data=jpeg_bytes,
            headers={"Content-Type": "image/jpeg"},
            timeout=5,
        )
    except Exception as e:
        # ส่งภาพไม่สำเร็จต้องไม่ทำให้การส่งค่าหยุด — ค่าสำคัญกว่าภาพ
        print(f"ส่ง snapshot ไม่สำเร็จ: {e}")
```

> ⚠️ จุดสำคัญในโค้ดข้างบน: **ส่งภาพล้มเหลวต้องไม่ทำให้ loop หลักหยุด**
> ค่าที่อ่านได้สำคัญกว่าภาพเสมอ ถ้า HTTP timeout แล้วโปรแกรมตาย จะเสียทั้งสองอย่าง

### ทำไมส่งเฉพาะตอนไม่ปกติ

ภาพตอนอ่านค่าได้ปกติแทบไม่มีใครเปิดดู แต่**ภาพตอน `UNREADABLE` คือหลักฐานว่าทำไมถึงอ่านไม่ออก** —
แสงสะท้อน? มีอะไรบัง? หลุดโฟกัส? สั่น? ซึ่งเป็นกุญแจแก้ปัญหาที่ตอนนี้อ่านไม่ออกอยู่ **47%**
(34,040 จาก 71,913 แถว ณ 2026-08-28) ซึ่งยังสูงมาก

ถ้าอยากได้ภาพตอนปกติไว้เทียบด้วย เสนอให้ส่ง **วันละไม่กี่ใบก็พอ** (เช่นทุก 6 ชั่วโมง)

## 4. ฝั่งเราจะทำอะไร

- เก็บภาพ **เป็นไฟล์บนดิสก์ ไม่เก็บลงฐานข้อมูล** — DB เก็บแค่ path
  (ถ้ายัดลง DB ไฟล์ backup จะบวมตามทันที และ retention ของค่ากับของภาพควรคนละอายุ)
- retention ของภาพสั้นกว่าของค่ามาก (ภาพกินที่มากกว่าหลายเท่า)
- จำกัดขนาดต่อไฟล์ และปฏิเสธถ้าเกิน — จะตอบกลับเป็น HTTP error พร้อมเหตุผล
- แสดงภาพบนการ์ดของจุดนั้นบนหน้า dashboard

**ยังไม่ได้เริ่มทำ** รอตกลงกันก่อนว่าจะเอาแนวนี้ไหม

## สิ่งที่ทำได้ดีอยู่แล้ว (ไม่ต้องแก้)

- payload ตรงสัญญา **100%** — `invalid` = 0 ทุกข้อความตั้งแต่เริ่มส่ง
- ตั้ง **LWT** ถูกต้อง ระบบรู้ทันทีที่ edge หลุด ไม่ค้างโชว์ค่าเก่า
- ส่ง `UNREADABLE` แทนการส่ง `0` เวลาอ่านไม่ออก ← ข้อนี้สำคัญมากและทำถูก
- heartbeat มาครบ (`sw=1.0.0` `model=hough-polar-v1`)
