# WORKFLOW — plan → design → tickets → ทำทีละใบ

กติกาการทำงานกับ AI สำหรับงานที่ใหญ่กว่า "แก้บั๊กจุดเดียว".
เป้าหมาย: คิดก่อนเขียน, งานย่อยตรวจรับได้, ไม่หลุด scope, ผู้ใช้ตามทันทุกก้าว.

## เส้นทางงาน

```
คุยเป้าหมาย → DESIGN → แตก TICKETS → ทำทีละใบ → VERIFY → CHANGELOG → confirm → ใบต่อไป
```

### 1) คุยเป้าหมาย (5-15 นาที ก่อนเขียนอะไร)
- ปัญหาคืออะไร / ใครใช้ / นิยาม "เสร็จ" คืออะไร
- ถ้าเป้ายังคลุม → AI ต้องถามจนชัด (ห้ามเดาแล้วลุย)
- เรื่องที่มีทางเลือก (DB? framework? โครงสร้าง?) → เปรียบเทียบ trade-off สั้นๆ ให้ผู้ใช้เคาะ
  แล้ว**จดลง `DECISIONS.md` ทันที** (กันถกซ้ำในอนาคต)

### 2) Design (งานที่แตะ >2 ไฟล์ หรือมี hardware/integration)
- เขียน/อัปเดต `ARCHITECTURE.md`: ภาพรวม + data flow + ขอบเขต layer
- กฎออกแบบที่พิสูจน์แล้วจากงานเก่า:
  - **config อยู่ในไฟล์ config** (yaml/pydantic) ไม่ hardcode — validate ตอนเปิดแอป ให้พังเสียงดังตั้งแต่ start
  - **layer แยกหน้าที่**: กล้อง/เซนเซอร์ไม่รู้จัก DB/UI ; UI ไม่คุย hardware ตรง ; ต่อกันผ่าน signal/queue
  - **hardware I/O = single-writer + lock** (serial/Modbus ไม่ thread-safe — บทเรียน RS485 race)
  - **อย่า block UI thread** — งานหนัก (inference/IO) อยู่ worker thread เสมอ ; งานที่วิ่งทุก frame ต้อง throttle
  - **fail อย่างปลอดภัย**: "ตรวจไม่ได้" ≠ "ของเสีย" ; อย่า reject ของดีเพราะระบบพลาด — log + แจ้ง อย่าเงียบ

### 3) แตกเป็น tickets (ลง `TICKETS.md`)
- 1 ใบ = จบใน 1 รอบทำงาน (ครึ่งวัน-1 วัน) + verify ได้ด้วยตัวเอง
- ทุกใบต้องมี `done-when` ที่วัดได้จริง (ไม่ใช่ "ทำให้ดีขึ้น")
- เรียง priority: P1 = ต้องมี / P2 = ควรมี / P3 = เผื่อมีเวลา

### 4) ทำทีละใบ
- เปิดใบ → อธิบายไทยว่าจะแก้ตรงไหนเพราะอะไร → แก้ → verify → CHANGELOG → **หยุดรอ confirm**
- เจอของนอก scope ระหว่างทาง → เปิด ticket ใหม่ ไม่แถมในใบเดิม

### 5) Verify (definition of done ทุกใบ)
- [ ] compile/import ผ่าน + test เดิมผ่านครบ (อย่าให้จำนวน test ลด)
- [ ] logic ใหม่มี smoke test พิสูจน์จริง (ไม่ใช่ "น่าจะได้")
- [ ] `CHANGELOG.md` อัปเดต (ทำอะไร + verify ยังไง)
- [ ] ถ้าโปรเจกต์ส่งมอบแล้ว → เข้า checklist `DEPLOYMENT.md` (แก้บนเครื่อง dev ไม่นับว่าเสร็จ)
