## D-015 เพิ่มปุ่มสลับธีมมืด/สว่างใน production (ล้ม scope เดิมของ D-014)  (2026-09-01)
เลือก:      ปุ่มสลับ 2 ตัวที่ topbar เขียน `data-theme` บน `<html>` + จำค่าไว้ใน `localStorage`
            ("meter-theme") ; script เล็ก ๆ ใน `index.html` อ่านค่าก่อน React mount กันจอกระพริบขาว
            ตอนโหลดหน้าถ้าเลือกธีมมืดไว้ ; โครงการ์ด/banner/confidence bar ใช้ร่วมกันทั้งสองธีม
            ต่างกันแค่ค่าใน CSS variable
แทนที่จะ:   ไม่ทำ toggle ในของจริง (มติเดิมใน D-014: "mock ทำหน้าที่ตรงนั้นพอ")
เพราะ:      ผู้ใช้ขอเพิ่มหลัง deploy จริงแล้วเห็นว่าอยากเทียบบนจอ production กับข้อมูลสดตรง ๆ
            ไม่ต้องพกไฟล์ mock ไปเปิดแยก — เหตุผลเดิมที่กลัวโค้ด 2 ชุดไม่ใช่ปัญหาจริงเพราะ
            สีทั้งหมดผ่าน CSS variable อยู่แล้วตั้งแต่ D-014 (เพิ่มแค่ override block เดียว)
สิ่งที่เจอระหว่างทำ: 🔴 ธีมมืดของเดิม (ก่อน D-014) มีบั๊ก contrast เดียวกับที่ audit เจอในธีมสว่าง
            ทั้ง 3 จุด (`--dim` 3.77-3.99:1, `--dead` 3.29-3.47:1, `--line` 1.36:1) — ไม่ได้เอาค่าเดิม
            กลับมาทั้งดุ้น คำนวณใหม่ให้ผ่าน AA เหมือนกัน (`--dim` 7.27:1, `--dead` 5.72:1,
            `--line` 3.31:1) · เจอ hardcoded `rgba(R,G,B,A)` อิงสีธีมสว่างตรง ๆ 13 จุดทั่วไฟล์
            (badge, chip, gauge-track, err panel ฯลฯ) ที่จะไม่สลับสีให้อัตโนมัติถ้าไม่แก้ —
            เปลี่ยนเป็น `color-mix(in srgb, var(--x) N%, transparent)` ทั้งหมด
trade-off:  ต้องคำนวณ/ทดสอบ contrast อีกชุดสำหรับธีมมืด (ทำไปแล้วในรอบนี้) ; เพิ่ม token
            `--panel-solid` กับ `--track` แยกจาก `--panel` เพราะธีมมืด panel โปร่งแสง
            ใช้แทนพื้นทึบ (แผงรายละเอียด) หรือเป็น track ของเกจไม่ได้ตรง ๆ
ทบทวนเมื่อ: ถ้าพบว่าไม่มีใครกดสลับธีมเลยหลังใช้งานจริงสักพัก อาจตัด toggle ออกแล้วให้เลือก
            ผ่าน config แทน (ลดพื้นผิว UI ที่ต้องดูแล)

## D-014 เปลี่ยนธีมเป็นพื้นสว่าง + ขอบหนาแทนเงา (แก้ 3 จุดที่ audit accessibility เจอ)  (2026-08-31)
เลือก:      พื้นขาว/เทาอ่อน + ขอบการ์ด 2px (ผิดปกติ 4px) แทนเงานุ่ม 1px ; ค่าเก่า/ออฟไลน์
            ใช้ **ขอบประ** เป็นตัวหลักแทน opacity อย่างเดียว ; ตัด text-shadow/glow ทั้งหมด ;
            สีทุกคู่ตัวหนังสือ-พื้นคำนวณผ่านสูตร WCAG relative luminance จริง ไม่กะด้วยตา
แทนที่จะ:   ธีมมืด "Liquid Industrial" เดิม (D-011)
เพราะ:      1) ทีมทดสอบ `docs/mock/theme-mock.html` (เทียบมืด/สว่าง × การ์ดเดิม/ใหม่ ×
               ภาพจากกล้อง/เกจ 8 คู่) แล้วเอนไปทางสว่าง+กรอบใหม่
            2) audit accessibility (WCAG 2.2 AA) เจอ 3 จุดที่ธีมมืดเดิม contrast ไม่ผ่าน —
               **เป็นบั๊กที่ deploy อยู่จริงบน Pi** ไม่ใช่แค่ปัญหาของ mock: ตัวหนังสือรอง
               `--dim` (เดิม 3.77-3.99:1 ต้องการ 4.5:1), ป้ายสถานะออฟไลน์/ค่าเก่า `--dead`
               (เดิม 3.29-3.47:1), ขอบการ์ดปกติ `--line` (เดิม 1.36:1 ต้องการ 3:1 — Critical
               เพราะการ์ด "ปกติ" ส่วนใหญ่พึ่งเส้นนี้เป็นตัวเดียวที่บอกว่าเป็นการ์ดแยกใบ)
            3) opacity อย่างเดียวสำหรับค่าเก่า/ออฟไลน์ใช้กับพื้นขาวไม่ได้ (เจอตอนทำ mock —
               การ์ดยังขาวอยู่ แค่ตัวหนังสือจาง ตาอ่านว่า "ปกติแต่เบลอ" ไม่ใช่ "เชื่อไม่ได้")
               → เปลี่ยนเป็นขอบประ ซึ่งใช้ได้ทั้งสองธีม
scope:      แก้ไฟล์เดียว `src/web/styles.css` — ตรวจแล้วว่า component TSX ทุกไฟล์ไม่มีสี
            hardcode นอก CSS variable เลย ; **ไม่ทำ runtime toggle มืด/สว่างในของจริง**
            เพราะ mock ที่มีอยู่แล้วทำหน้าที่ทดสอบ/ตัดสินใจตรงนั้นพอ เพิ่ม toggle ในของจริง
            จะเป็นโค้ด 2 ชุดที่ต้องดูแลตลอดไปโดยไม่จำเป็น
trade-off:  ยังไม่ได้ยืนดูบนจอ Pi จริงที่หน้างาน (ทดสอบผ่าน mock บนจอ dev/Pi แยกต่างหาก) ;
            ถ้าทีมกลับไปเอาธีมมืดตอนดูจอจริง ต้อง revert ไฟล์เดียวนี้ — เก็บ commit ก่อนหน้า
            ที่เป็นธีมมืดไว้อ้างอิงได้เสมอ (git log)
ทบทวนเมื่อ: เอาไปเปิดจอ Pi จริงที่โรงงานแล้วทีมยืนยัน/เปลี่ยนใจ

## D-013 ส่ง snapshot ผ่าน MQTT topic แยก ไม่ใช่ HTTP  (2026-08-28)
เลือก:      MQTT topic `<prefix>/<device_id>/snapshot/<frame_id>` · ไบต์ดิบ ไม่ base64 ·
            `retain=false` · เฉพาะตอน `quality != OK` · เพดาน 1 ภาพ/นาที/จุด
แทนที่จะ:   `POST /api/frames/:frame_id/snapshot` (ทาง A ที่เสนอไว้ตอนแรก)
เพราะ:      1) **ได้ auth ฟรีตอนทำ T-008** — endpoint HTTP รับไฟล์ที่ไม่มี auth คือช่องให้ใครก็ได้
               ในวง LAN ยิงจนดิสก์เต็ม ถ้าใช้ MQTT พอใส่ user/password + ACL ให้ broker
               ภาพได้รับการป้องกันไปด้วยทันที ไม่ต้องทำ auth สองชุด
            2) edge มี connection เดียว ไม่ต้องดูแล failure mode ที่สอง (timeout/retry ของ HTTP)
            3) ถ้าเครือข่ายโรงงานจริงเข้มกว่าออฟฟิศ MQTT ผ่านอยู่แล้วแน่ ๆ
trade-off:  ภาพผ่าน broker persistence = เขียน SD เพิ่มอีกรอบ
            **แต่พอใส่เพดานแล้วเหลือ ~36-54 MB/วัน = ~13-20 GB/ปี ซึ่งเทียบกับ endurance
            ของ SD (หลายสิบ TB) แล้วเป็นเศษเสี้ยว** — ตอนเสนอทาง A ผมยกข้อนี้มาโดยคิดจาก
            ตัวเลขก่อนใส่เพดาน (1.3 GB/วัน) ซึ่งให้น้ำหนักผิด ;
            และไม่ได้ backpressure แบบ HTTP ต้องกันด้วย message_size_limit แทน
ทบทวนเมื่อ: ปริมาณภาพโตเกิน ~200 MB/วัน หรือ broker เริ่มเป็นคอขวด

## D-012 บีบที่ ingest แทนการหา DB ที่เก็บได้เยอะขึ้น  (2026-08-27)
เลือก:      throttle ตอน ingest (deadband + เพดานอัตรา + บังคับเก็บทุก 60 วิ) + retention 30 วัน
แทนที่จะ:   ใส่ TimescaleDB / partition เพื่อรองรับปริมาณตามที่ D-002 เปิดช่องไว้
เพราะ:      **D-002 ประเมินอัตราผิด** — เขียนไว้ว่า "ทุกไม่กี่วินาที" แต่วัดจากของจริงได้
            **26 เฟรม/วินาที** (2298 แถวใน 87 วิ) = 830 MB/วัน ต่อจุดวัดเดียว SD เต็มใน ~23 วัน ;
            แต่ต้นตอไม่ใช่ DB เก็บไม่ไหว — คือ **เก็บค่าที่ไม่มีความหมาย** เข็มมิเตอร์ไม่ได้ขยับ
            26 ครั้ง/วินาที Timescale จะแค่บีบอัดสายน้ำที่ไม่ควรไหลแรงขนาดนั้นตั้งแต่แรก ;
            พอ throttle แล้วปริมาณเหลือระดับที่ DELETE + autovacuum เอาอยู่ ไม่ต้อง partition (D-007)
trade-off:  ทิ้งค่าระหว่างกลางที่อยู่ใน deadband — ถ้าวันหนึ่งต้องวิเคราะห์ย้อนหลังละเอียดระดับ
            ทุกเฟรม จะไม่มีข้อมูลให้ ; และ **ถ้าโมเดลกระพริบ OK↔UNREADABLE ถี่ ๆ
            throttle จะช่วยได้น้อยลง** (วัดได้ 2.9 แทนที่จะเป็น 1 แถว/วิ/จุด)
            เพราะการเปลี่ยนสถานะสำคัญเกินกว่าจะทิ้ง — ต้องแก้ที่ต้นทาง (กล้อง/แสง) ไม่ใช่ที่นี่
ทบทวนเมื่อ: ทีม AI ใส่ throttle ฝั่ง edge แล้ว (จะยิ่งดีเพราะประหยัดเน็ต+CPU ของ Pi 4 ด้วย) ;
            หรือมีความต้องการวิเคราะห์ย้อนหลังละเอียดระดับทุกเฟรม

            3) **sidebar 6 เมนู + แถบแจ้งเตือน + ปุ่มวินิจฉัย** → เป็นฟีเจอร์ที่ยังไม่มีของจริง

            (~150-250KB ลง repo) ; ไม่มี sidebar ทำให้ดูโล่งกว่าภาพต้นแบบ
ทบทวนเมื่อ: มีหน้าอื่นให้ลิงก์ไปจริง (รายเครื่อง/ประวัติ/รายงาน) → ค่อยทำ sidebar ;
            หรือมีระบบ alarm (ซึ่งยังรอทีม AI ตอบว่าใครเป็นคนตัดสิน)

เลือก:      สเกลหน้าปัด (min_value/max_value) อยู่ที่ระดับ point ; fixture เก็บแค่เรขาคณิตในภาพ
แทนที่จะ:   รวมไว้ใน gaugeFixture เหมือน record ใน bench/samples.json
เพราะ:      สองอย่างเปลี่ยนคนละจังหวะ — ขยับกล้อง fixture เปลี่ยนแต่สเกลเท่าเดิม /
            เปลี่ยนตัวมิเตอร์ สเกลเปลี่ยนแต่กล้องเท่าเดิม ; และ UI ต้องใช้สเกลวาดเกจ
            ถ้าฝังใน fixture จะวาดไม่ได้เลยจนกว่าจะมีคนตั้งกล้องเสร็จ (fixture เป็น null อยู่)
trade-off:  ต่างจาก samples.json ที่ทีม AI คุ้นเคย ต้องอธิบายตอนส่งสัญญาให้เขาดู ;
            ข้อมูลสเกลอยู่คนละที่กับที่ AI ใช้แปลงมุมเป็นค่า ต้องส่งทั้งสองส่วนลงไปตอน push config
ทบทวนเมื่อ: ทีม AI บอกว่าอยากรับเป็นก้อนเดียวแบบ samples.json

## D-008 ingest ต้อง idempotent — unique (point_id, frame_id)  (2026-08-26)
เลือก:      unique index บน (point_id, frame_id) + INSERT ... ON CONFLICT DO NOTHING
แทนที่จะ:   จำ frame_id ล่าสุดต่อเครื่องไว้ในหน่วยความจำ / ไม่ทำอะไรเลย
เพราะ:      MQTT QoS 1 = at-least-once ตามสเปก ข้อความซ้ำเป็นเรื่องปกติไม่ใช่ความผิดปกติ ;
            เฟรมล่าสุดเป็น retained → ทุกครั้งที่ ingest subscribe ใหม่ (restart/สายหลุด)
            จะได้เฟรมเก่ากลับมาทั้งชุด การจำในหน่วยความจำแก้ไม่ได้เพราะ restart แล้วลืม
trade-off:  index เพิ่มอีกตัวบนคอลัมน์ text สองอัน กินพื้นที่บน SD ที่มีจำกัด (D-006) ;
            ถ้าทีม AI ส่ง frame_id ซ้ำสำหรับเฟรมคนละอัน ข้อมูลจริงจะถูกกลืนหายไปเงียบ ๆ
ทบทวนเมื่อ: ทีม AI ยืนยันกติกาการตั้ง frame_id ; ถ้าเขาไม่รับประกันว่า unique
            ต้องเปลี่ยนไป dedup ด้วย (point_id, captured_at) แทน

## D-007 ยังไม่ partition ตาราง readings — ทำ BRIN ก่อน  (2026-08-26)
เลือก:      ตาราง readings ธรรมดา + BRIN บน captured_at + btree (point_id, captured_at DESC)
แทนที่จะ:   partition รายเดือนตั้งแต่แรกตามที่ D-002 เขียนไว้
เพราะ:      Postgres ไม่สร้าง partition ให้เอง — ถ้าไม่มีงานสร้างล่วงหน้า พอขึ้นเดือนใหม่
            INSERT จะ error ทันที = ข้อมูลหายตอนเที่ยงคืนวันที่ 1 บนเครื่องที่ไม่มีคนเฝ้า ;
            ยังไม่รู้อัตรายิงจริงจากทีม AI จึงยังไม่รู้ว่าคุ้มไหม ; แปลงทีหลังตอนตารางเล็กยังถูก
trade-off:  ถ้าปล่อยจนตารางโตมากค่อยแปลง ต้องมี downtime สั้น ๆ ตอน copy ข้อมูล ;
            การลบข้อมูลเก่าจะเป็น DELETE (ทำให้ตารางบวม ต้อง VACUUM) แทน DROP PARTITION ที่ทันที
ทบทวนเมื่อ: รู้อัตรายิงจริง หรือใกล้ production (พื้นที่บน SD เริ่มตึง) → ทำ T-009

## D-006 Postgres อยู่บน SD ไปก่อน + pg_dump cron  (2026-08-26)
เลือก:      เก็บ data ของ Postgres บน SD card ของ Pi + ตั้ง pg_dump cron ส่งออกไปเครื่องอื่น
แทนที่จะ:   ซื้อ NVMe HAT + SSD มาใส่ตั้งแต่ตอนนี้
เพราะ:      ยังเป็นช่วง dev ยังไม่มีข้อมูลจริงที่เสียไม่ได้ ; ความเสี่ยงหลักคือไฟดับกลางคัน
            ทำให้ DB corrupt (ไม่ใช่ SD สึก — write rate ต่ำมาก) ซึ่ง dump ที่อยู่นอกเครื่องกู้ได้
trade-off:  ไฟดับแล้ว corrupt = เสียข้อมูลตั้งแต่ dump ล่าสุดถึงตอนดับ ; ต้องไม่ลืมตั้ง cron จริง
            ไม่งั้นการตัดสินใจนี้กลายเป็นการยอมรับความเสี่ยงเปล่า ๆ
ทบทวนเมื่อ: ก่อนส่งมอบ/ใช้งานจริงในโรงงาน — ตอนนั้นควรอัปเกรดเป็น NVMe + UPS

## D-005 ใช้ MQTT LWT ประกาศเครื่องตาย ไม่พึ่งโค้ดตอนปิดตัวเอง  (2026-08-25)
เลือก:      LWT (Last Will and Testament) + topic `<prefix>/<device>/device_status` แบบ retained
แทนที่จะ:   ล้าง retained frame ใน SIGINT/SIGTERM handler ตอน process ปิด
เพราะ:      handler ตอนออกไม่ครอบคลุมสิ่งที่เกิดจริงกับ edge ในโรงงาน — ไฟดับ สายหลุด kill -9
            ล้วนไม่มีโอกาสรันโค้ด ; และพิสูจน์แล้วว่าบน Windows/Bun สัญญาณไม่ถึง JS เลย
            (exit 143 handler ไม่ทำงาน retained ค้างครบ 3) ; broker เท่านั้นที่ประกาศแทนได้
trade-off:  เพิ่มข้อกำหนดให้ทีม AI — edge ทุกตัวต้องตั้ง LWT เอง (OPEN-7 ใน contract/messages.ts)
            ถ้าเขาไม่ทำ เราจะแยก "ตาย" กับ "ยังไม่ถึงรอบส่ง" ไม่ออก ; retained frame ยังค้างอยู่
            ผู้อ่านต้องดู device_status ควบคู่เสมอ ไม่ใช่ดูแต่ค่า
ทบทวนเมื่อ: ทีม AI ยืนยันว่าตั้ง LWT ไม่ได้ → ต้องถอยไปใช้ heartbeat timeout ซึ่งช้ากว่าและพลาดง่ายกว่า
✅ ทดสอบบน Pi 5 (Linux) 2026-08-26: เส้นทาง **ปิดแบบสุภาพ (Ctrl+C) ทำงานจริง** → OFFLINE ครบ 3
   ซึ่งบน Windows ทดสอบไม่ได้เลยเพราะ signal ไปไม่ถึง JS — ยืนยันว่าโค้ด handler ถูกต้อง
   เส้นทาง **LWT (kill -9) ยืนยันบน Pi แล้ว**: เห็น ONLINE → ฆ่าดิบ → พลิกเป็น OFFLINE จริง
   (เทสรอบแรกสรุปไม่ได้เพราะ retained ค้างจากรอบก่อน ต้องคุมลำดับให้เห็น ONLINE ก่อนเสมอ)

## D-002 Postgres 17 ล้วน ยังไม่เอา TimescaleDB  (2026-08-25)
เลือก:      Postgres 17 ใน Docker + partition รายเดือน + BRIN index บนคอลัมน์เวลา
แทนที่จะ:   TimescaleDB ตั้งแต่ต้น / InfluxDB
เพราะ:      3 device × จุดวัดหลักสิบ × ทุกไม่กี่วินาที ยังไม่ถึงล้านแถว/วัน — Postgres ล้วนรับไหวบน Pi 5 ·
            `create_hypertable()` แปลงตารางที่มีข้อมูลแล้วได้ → เติมทีหลังไม่แพง ·
            InfluxDB จะกลายเป็น DB ตัวที่สองเพราะยังต้องมี Postgres เก็บ config อยู่ดี
trade-off:  ถ้าอัตรายิงสูงกว่าประเมินมาก ต้องทำ rollup รายนาที/ชั่วโมงเองด้วย materialized view + cron
ทบทวนเมื่อ: อัตรายิงจริงจากทีม AI ชัด หรือตาราง readings โตเกิน ~50M แถว
⚠️ ยังไม่รู้อัตราจริง — ตัวเลขข้างบนเป็นการประเมิน ไม่ใช่ข้อมูลจากทีม AI

## D-001 Vite + React + Hono ไม่เอา Next.js  (2026-08-25)
เลือก:      Bun + Hono (API + SSE + เสิร์ฟ static) + Vite/React แยก build
แทนที่จะ:   Next.js 16 เหมือน YoshiOpspectWebsite / FastAPI + Jinja
เพราะ:      **MQTT subscriber อยู่ใน process เดียวกับ API ได้** — Next ทำไม่ได้ (route handler
            ค้างฟัง subscription ไม่ได้) ต้องแยก worker + คุยผ่าน DB/NOTIFY = ชิ้นส่วนเพิ่มบนเครื่องหน้างาน ·
            เหลือ systemd unit เดียว · build บน Pi ~10 วินาทีแทน 2-5 นาที · node_modules ~150MB แทน ~600MB
            (สำคัญเพราะบูตจาก SD เหลือ 19GB) · โปรเจกต์มีแค่ 3-4 หน้า ไม่ต้องใช้ SSR/RSC
trade-off:  ต้องประกอบ routing/data-fetching เอง (React Router + TanStack Query) ไม่มีของแถมแบบ Next ·
            เหตุผลเดิมที่เคยเชียร์ Next คือ reuse ของพี่ Sun ซึ่งตกไปพร้อม D-004
ทบทวนเมื่อ: หน้าเว็บโตเกิน ~10 หน้า หรือต้องการ SSR เพื่อ SEO/first paint จริงจัง
✅ ยืนยันบนเครื่องจริง 2026-08-26: `bun run build` บน Pi 5 arm64 = **178ms**
   (เครื่อง dev Windows 186ms) — สมมติฐานเรื่องความเร็ว build ถูกต้อง และ Bun บน arm64 ไม่มีปัญหา (D-003)
