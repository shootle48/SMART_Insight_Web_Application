## D-024 สินค้า 2 ระดับ — ระดับตัวถูก: Zero ส่งภาพ + โมเดลรันบน Pi 5 ในฐานะ "edge อีกตัว"  (2026-09-11)
เลือก:      Pi Zero 2 W รันโมเดลไม่ไหว (RAM 415MB) → ทีมแยกสินค้าเป็น 2 ระดับ
            - **ตัวถูก**: Zero ส่งภาพดิบอย่างเดียว → โมเดล 7SEG/WATER_METER รันบน Pi 5
              เครื่องเดียวกับ UI/broker/DB ของเรา
            - **ตัวปกติ**: edge คิดเอง 1 เครื่อง 1 โมเดล (แบบที่ทำอยู่)
            เคาะ 4 ข้อ (T-027):
            1. **ภาพดิบส่งผ่าน MQTT broker ตัวเดิม พอร์ตเดิม** (1883)
            2. **โมเดลบน Pi 5 publish เข้า broker ตัวเดิมด้วยสัญญาเดิม** (`meter_frame` ฯลฯ)
               ⇒ server เราเห็นมันเป็น edge อีกตัว **แยกไม่ออกว่าเป็นระดับไหน**
            3. **ทีม AI ลงโมเดลบน Pi 5 เอง** — ไม่ใช่ของใน repo/deploy ของเรา
            4. **แยก profile กัน** — โค้ดเรากับโมเดลเขาแค่อยู่ร่วมเครื่องกัน ไม่ผูกกัน
แทนที่จะ:   ให้โมเดลคุยกับ server เราตรง (HTTP/ไฟล์) · หรือเอาโมเดลเข้ามาใน repo เรา ·
            หรือทำ profile เดียวที่รู้จักทั้ง 2 ระดับ
เพราะ:      1) ข้อ 2 คือหัวใจ — **รักษา seam ที่ T-002/D-002 วางไว้**: ทุกอย่างที่คุยกับเราต้อง
               ผ่านสัญญา MQTT ชุดเดียว ; โค้ดที่ทำมาทั้งหมด (ingest/throttle/alarm/evidence/
               calibrate) ใช้ได้ทันทีโดยไม่แก้ และ `PUBLISHING-GUIDE.md` ยังใช้ได้ทั้งฉบับ
            2) ข้อ 3+4 ทำให้ **D-020 "ฝั่ง edge นอกขอบเขต" ยังจริง** — แค่ขอบเขตย้ายจาก
               "คนละเครื่อง" เป็น "คนละ process" ; โมเดลพังยังเป็นของทีม AI เหมือนเดิม
            3) MQTT พอร์ตเดิมสำหรับภาพดิบ = ไม่เพิ่มช่องทาง/auth ชุดที่สอง (เหตุผลเดียวกับ D-013)
scope:      ยังไม่แก้โค้ด — เอกสารก่อน ; งานจริงที่ตามมา: **T-029** (broker/ingest กันภาพดิบ) ·
            **T-030** (สัญญา+คู่มือสำหรับทีม AI เรื่อง topic ภาพดิบและสถานะต่อ Zero) ·
            **T-028** ปลดบล็อก (soak test)
trade-off:  - 🔴 **ภาพดิบทุกเฟรมวิ่งผ่าน broker เรา** — คนละโลกกับ evidence ของ D-013 ที่เป็น
              "1 ภาพ/นาที/จุด เฉพาะตอนอ่านไม่ออก" ; ต้องเป็น **topic แยก ที่ ingest ไม่ sub**
              (ไม่งั้นนับเป็น invalid — กับดักเดิมของ T-011) และต้องเป็น **QoS 0 ไม่ retain**
              ให้ broker ไม่ persist ลง SD และโมเดลตายแล้วเฟรมแค่หล่นหาย ไม่กองรอ
            - 🔴 **โมเดล process เดียว publish แทนหลาย Zero = LWT ตัวเดียว** — `device_status`
              ผ่าน LWT (D-005) จะบอกได้แค่ "โมเดลตาย" **แยกไม่ออกว่า Zero ตัวไหนหยุดส่ง**
              ⇒ โมเดลต้อง publish `device_status OFFLINE` ต่อ Zero เองเมื่อเฟรมหยุดมา
              (กติกาใหม่ที่ต้องเขียนลงคู่มือ — T-030) ; ระหว่างที่ยังไม่ทำ UI จะเห็น Zero ที่
              ตายเป็น "ไม่ส่งข้อมูล" (stale) แทนที่จะเป็น "ออฟไลน์" — ยังพอใช้ได้แต่ช้ากว่า
            - ⚠️ **ทรัพยากรบน Pi 5 ถูกแย่ง** — โมเดลกับ Chromium/Postgres แชร์ CPU ; ใครแย่ง
              ใครยังไม่รู้จนกว่า T-028 จะวัด ; และเรื่อง thermal ไม่ใช่ปัญหาของโมเดลอย่างเดียว
              แต่ทำให้ **ทุกอย่างบนเครื่องช้าลงพร้อมกัน** รวมถึงจอ
            - `DEPLOYMENT.md` ของเราจะ**ไม่ครบ**สำหรับระดับตัวถูก — ต้องมีบรรทัดชี้ว่า "โมเดล
              ทีม AI ลงแยก ดูคู่มือของเขา" ไม่งั้นคนติดตั้งจะคิดว่าเสร็จแล้วทั้งที่ยังอ่านค่าไม่ได้
ทบทวนเมื่อ: T-028 วัดแล้วพบว่า Pi 5 รับกล้องได้น้อยจนไม่คุ้ม (ต้องกลับไปคิดเรื่องเครื่องกลาง
            แยก) · หรือทีม AI ทำ per-Zero status ไม่ได้ · หรือปริมาณภาพดิบผ่าน broker ทำให้
            ค่าจริงมาช้า (broker เป็นคอขวด — ตอนนั้นต้องแยก broker หรือเปลี่ยนช่องทางภาพ)

## D-023 alarm/threshold — ตัดสินที่ ingest, ระดับเดียว, เปลี่ยนสถานะต้องยืนยัน N ครั้ง  (2026-09-10)
เลือก:      ทีมขอระบบแจ้งเตือนเมื่อค่าออกนอกช่วงที่กำหนด (เช่น gauge ต้องอยู่ 100–150)
            — **ตอบ OPEN-6 ที่ค้างอยู่ใน `contract/messages.ts` มาตั้งแต่ต้น**
            1. **ฝั่งเราคำนวณ ไม่ใช่ edge ส่งสถานะมา** — edge อยู่นอกขอบเขต (D-020) สั่งไม่ได้
            2. **ตัดสินที่ ingest แล้วเก็บสถานะลง DB** ไม่ใช่คำนวณสดที่หน้าเว็บ
            3. **ระดับเดียว: ปกติ / ผิดปกติ** ไม่มี "เตือน" กับ "วิกฤต" แยกกัน
            4. **เกณฑ์เป็นคอลัมน์ใหม่ แยกจาก `min_value`/`max_value` เด็ดขาด**
            5. **เปลี่ยนสถานะต้องเกินเกณฑ์ติดกัน N ครั้ง** (default 3, ตั้งได้ที่ `.env`)
แทนที่จะ:   คำนวณที่หน้าเว็บล้วน · หรือใช้ `min_value`/`max_value` เป็นเกณฑ์ไปเลย ·
            หรือเด้งทันทีที่เจอค่าแรกที่เกิน
เพราะ:      1) หน้าเว็บคำนวณเองจะ **ไม่รู้ว่าเคยเตือนไปแล้ว** — รีเฟรชหน้าทีก็เด้งซ้ำทุกครั้ง
               และแต่ละเบราว์เซอร์ที่เปิดอยู่จะเด้งไม่ตรงกัน ; สถานะใน DB ทำให้มีความจริงชุดเดียว
            2) **`min/max` คือสเกลของหน้าปัด ไม่ใช่ช่วงที่ยอมรับได้** — เกจอ่านได้ 0–500 psi
               ไม่ได้แปลว่า 480 เป็นค่าปกติ ; ผู้ใช้ระบุชัดว่าคนละเรื่องกัน และ D-010 ก็แยก
               สเกลออกจาก fixture ด้วยเหตุผลทำนองเดียวกันมาแล้ว
            3) 🔴 **ถ้าเด้งทุกค่าที่เกิน จะได้ noti ~10,000 อันเมื่อค่าค้างนอกเกณฑ์ 3 ชั่วโมง**
               (throttle เก็บราว 1 ค่า/วิ/จุด — D-012) ⇒ เด้งเฉพาะ**ตอนเปลี่ยนสถานะ**เท่านั้น
            4) 🔴 **ต้องยืนยัน N ครั้งเพราะ OCR อ่านพลาดได้** — UNREADABLE ยัง 47% แปลว่า
               โมเดลไม่นิ่ง ; ค่าเพี้ยนวูบเดียว (999 จากการอ่านผิด) ไม่ควรปลุกทั้งโรงงาน
               และยังกันค่าที่แกว่งรอบขอบเกณฑ์ (99.9 → 100.1) ไม่ให้เด้งรัวไปด้วยในตัว
            5) ระดับเดียวก่อนเพราะ **ยังไม่มีใครบอกว่าต้องแยกเตือน/วิกฤตจริง** — เพิ่มทีหลังได้
               โดยไม่ต้องรื้อ (แค่เติมคู่คอลัมน์) แต่ถ้าทำ 2 ระดับตั้งแต่แรกต้องกรอก 4 ช่องต่อจุด
               ซึ่งคนตั้งค่าหน้างานจะเลิกใช้
scope:      ยังไม่เขียนโค้ด — เอกสารก่อน แล้วแตกเป็น T-024 (backend) · T-025 (UI) ·
            T-026 (ฟอร์มตั้งเกณฑ์) ทำทีละใบ
trade-off:  - **ต้องเพิ่มคอลัมน์ + migration** ซึ่งหนักกว่าทำที่หน้าเว็บล้วน
            - **N ครั้ง = เตือนช้าลง ~N วินาที** ; รับได้เพราะงานนี้คือเฝ้าหน้าปัดในตู้
              ไม่ใช่ระบบตัดการทำงานฉุกเฉิน (ถ้าวันหนึ่งต้องตัดเครื่องจริง ต้องคิดใหม่ทั้งหมด)
            - 🔴 **`UNREADABLE` จะไม่ประเมินเกณฑ์เลย** (คงสถานะเดิมไว้) — ตามหลัก
              "ตรวจไม่ได้ ≠ ของเสีย" ใน ARCHITECTURE ; ผลข้างเคียงคือถ้าโมเดลอ่านไม่ออกยาว ๆ
              สถานะจะค้างที่ค่าล่าสุด **ซึ่งอาจไม่ตรงความจริงแล้ว** — ต้องดู "ค่าเก่า" คู่กันเสมอ
            - **ไม่ทำประวัติการเตือนในรอบนี้** (ตาราง alarm_events) — รู้ได้แค่ "ตอนนี้ผิดปกติ
              ตั้งแต่เมื่อไหร่" ยังตอบไม่ได้ว่า "อาทิตย์นี้เตือนกี่ครั้ง" ; เปิดใบใหม่ถ้าต้องการ
ทบทวนเมื่อ: มีคนขอแยกระดับเตือน/วิกฤต · หรือขอรายงานย้อนหลังว่าเตือนกี่ครั้ง ·
            หรือขอให้ระบบ**สั่งการ**อะไรตอนเตือน (ตรงนั้นจะเปลี่ยนจาก "จอเฝ้าดู" เป็น
            "ระบบควบคุม" ซึ่งเป็นคนละความรับผิดชอบ — ดูที่ตัดปุ่ม Emergency Stop ทิ้งใน D-011)

## D-022 calibration เหลือ GAUGE ชนิดเดียวถาวร — ตัด fixture ของ SEVEN_SEGMENT/WATER_METER  (2026-09-10)
เลือก:      ลบ `bboxSchema` + `sevenSegmentFixtureSchema` ออกจาก `contract/points.ts` และยุบ
            `pointFixtureSchema` จาก discriminatedUnion เหลือ `gaugeFixtureSchema` ตัวเดียว
            ; `config/<point_id>` จะถูก publish เฉพาะจุดที่เป็น GAUGE เท่านั้น
แทนที่จะ:   เก็บ schema ไว้เผื่อวันหนึ่งได้ใช้ (ตามที่ D-018 เคยวางไว้)
เพราะ:      1) ผู้ใช้ยืนยัน 2026-09-09 ว่า **SEVEN_SEGMENT กับ WATER_METER อ่านค่าด้วยโมเดล
               ไม่ใช่ computer vision** จึงไม่มีเรขาคณิตในภาพให้สอบเทียบ — ต่างจาก GAUGE
               ที่ต้องรู้ว่าเข็มชี้ตรงไหนถึงจะแปลงเป็นค่าได้ ; ไม่ใช่ "ยังไม่ได้ทำ" แต่เป็น
               "ไม่มีอะไรให้ทำ"
            2) schema ที่ไม่มีใครใช้แต่ยังอยู่ในสัญญา = คนอ่านทีหลังต้องเสียเวลาไล่ว่าใช้ตอนไหน
               และมีโอกาสที่ทีม AI จะไปทำ feature รองรับของที่เราไม่เคยส่งให้
            3) เผื่อไว้ล่วงหน้าโดยไม่มีของจริงรองรับ = การเดา ซึ่งโปรเจกต์นี้เจ็บมาแล้วกับ
               `LAMP` (D-016 — เดาเผื่อไว้ตอนออกแบบสัญญาแรก แล้วต้องมาตัดทีหลัง)
scope:      `contract/points.ts` (ลบ 2 schema + ยุบ union) · `web/apiClient.ts` (ตัด union ฝั่งเว็บ) ·
            `db/schema.ts` (คอมเมนต์) · `docs/CALIBRATION-PROPOSAL.md` (**ทำเครื่องหมาย
            ยกเลิก ไม่ลบทิ้ง** เพราะฉบับเก่าส่งให้ทีม AI ไปแล้ว ต้องให้เขาอ่านออกว่าถอนแล้ว)
trade-off:  - ถ้าวันหนึ่งมีหน้าปัดชนิดใหม่ที่ต้องสอบเทียบจริง ต้องกลับมาทำ union ใหม่ —
              ยอมจ่ายตรงนั้นตอนมีของจริง ดีกว่าเดาล่วงหน้าแล้วผิด
            - 🔴 **ทีม AI อาจเคยอ่านฉบับที่มี bbox ไปแล้ว** — ถ้าเขาเริ่มทำฝั่ง edge รองรับไว้
              จะเสียเปล่า ต้องแจ้งให้รู้ว่าถอนแล้ว
ทบทวนเมื่อ: มีหน้าปัดชนิดใหม่ที่ต้องบอกตำแหน่งในภาพถึงจะอ่านได้ (ไม่ใช่แค่โมเดลอ่านเอง)

## D-021 แยก token พื้นปุ่มหลักออกจาก `--primary` (สีแบรนด์ใช้เป็นพื้นปุ่มไม่ได้)  (2026-09-09)
เลือก:      เพิ่ม `--primary-btn` / `--primary-btn-hover` / `--on-primary-btn` แยกต่อธีม
            สำหรับ **พื้นปุ่มที่มีตัวหนังสือ** ; `--primary` เดิมคงไว้ใช้กับ rail/focus ring/สีเน้น
            - สว่าง: พื้น `#c2410c` + ตัวอักษรขาว (5.18:1 · แยกจากพื้นการ์ด 4.48:1)
            - มืด:   พื้น `#fe6e00` + ตัวอักษร `#2b2622` (5.31:1 · แยกจากพื้นการ์ด 4.06:1)
            และเพิ่ม `--on-primary: #2b2622` (ไม่แยกธีม) สำหรับไอคอนบนปุ่มสลับธีม ซึ่งอยู่บนแถบ
            `--shell` ที่เป็นสีมืดเหมือนกันทั้งสองธีม จึงใช้ `--primary` สดได้แต่ต้องใช้ไอคอนสีเข้ม
แทนที่จะ:   ใช้ `--primary` เป็นพื้นปุ่มตรง ๆ ตามที่โค้ดเดิมตั้งใจไว้ (แต่ไม่เคยทำงานจริง ดู T-021)
เพราะ:      1) **คำนวณจริงแล้ว `--primary` + ตัวอักษรขาว = 2.86:1 (สว่าง) / 2.82:1 (มืด)**
               ตกเกณฑ์ AA 4.5:1 ทั้งคู่ — ถ้าแก้แค่ specificity ให้ปุ่มเป็นสีส้มตามที่ตั้งใจ
               จะได้ปุ่มที่ "ดูถูกตามดีไซน์" แต่อ่านยากกว่าเดิม
            2) ทำตามแนวที่ D-014/D-015 วางไว้แล้ว — สีจาก design doc ที่ตกเกณฑ์ให้**คำนวณ
               เวอร์ชันที่ผ่านแยกต่อธีม** ไม่ใช่ปรับด้วยสายตาหรือยอมให้ตก
            3) ไม่แตะ `--primary` เพราะที่อื่นใช้ถูกอยู่แล้ว — rail/focus ring เป็น non-text
               ใช้เกณฑ์ 3:1 ซึ่งส้มสดผ่านสบาย ; ถ้าไปทำให้ `--primary` เข้มลงทั้งชุด สีเน้น
               ทั้งแอปจะหม่นลงโดยไม่จำเป็น
            4) ธีมมืดกลับด้านเป็น "ส้มสด + ตัวอักษรเข้ม" เพราะทางเลือกอื่นตันหมด: ส้มเข้ม
               `#c2410c` แยกจากพื้นการ์ดมืดได้แค่ 2.21:1 (ตก 1.4.11) ส่วนส้มที่สว่างพอจะแยก
               ออกจากพื้นมืดกลับรับตัวอักษรขาวไม่ไหว (`#e8590c` + ขาว = 3.58:1)

            4) DB เป็น source of truth ของ config (มี column `points.fixture` jsonb อยู่แล้ว) —
               broker retained store เป็น cache/distribution channel ให้ edge เท่านั้น
               ถ้าไม่ตรงกัน server publish ซ้ำจาก DB ได้เสมอ
scope:      ยังไม่เขียนโค้ด — เอกสารก่อน คุยกับทีม AI แล้วค่อยแตก T-013 (backend + broker)

trade-off:  - ต้องเพิ่ม MQTT client publish บน server ตอนนี้ (subscribe อย่างเดียว)
            - **T-008 (auth broker) ยังไม่เสร็จ** = ใครใน LAN ก็ยิง config ปลอมได้

## D-013 ส่ง snapshot ผ่าน MQTT topic แยก ไม่ใช่ HTTP  (2026-08-28)
เลือก:      MQTT topic `<prefix>/<device_id>/snapshot/<frame_id>` · ไบต์ดิบ ไม่ base64 ·
            `retain=false` · เฉพาะตอน `quality != OK` · เพดาน 1 ภาพ/นาที/จุด
แทนที่จะ:   `POST /api/frames/:frame_id/snapshot` (ทาง A ที่เสนอไว้ตอนแรก)
เพราะ:      1) **ได้ auth ฟรีตอนทำ T-008** — endpoint HTTP รับไฟล์ที่ไม่มี auth คือช่องให้ใครก็ได้
               ในวง LAN ยิงจนดิสก์เต็ม ถ้าใช้ MQTT พอใส่ user/password + ACL ให้ broker
               ภาพได้รับการป้องกันไปด้วยทันที ไม่ต้องทำ auth สองชุด
            2) edge มี connection เดียว ไม่ต้องดูแล failure mode ที่สอง (timeout/retry ของ HTTP)
            3) ถ้าเครือข่ายโรงงานจริงเข้มกว่าออฟฟิศ MQTT ผ่านอยู่แล้วแน่ ๆ
trade-off:  ภาพผ่าน broker persistence = เขียน SD เพิ่มอีกรอบ
            **แต่พอใส่เพดานแล้วเหลือ ~36-54 MB/วัน = ~13-20 GB/ปี ซึ่งเทียบกับ endurance
            ของ SD (หลายสิบ TB) แล้วเป็นเศษเสี้ยว** — ตอนเสนอทาง A ผมยกข้อนี้มาโดยคิดจาก
            ตัวเลขก่อนใส่เพดาน (1.3 GB/วัน) ซึ่งให้น้ำหนักผิด ;
            และไม่ได้ backpressure แบบ HTTP ต้องกันด้วย message_size_limit แทน
ทบทวนเมื่อ: ปริมาณภาพโตเกิน ~200 MB/วัน หรือ broker เริ่มเป็นคอขวด

## D-008 ingest ต้อง idempotent — unique (point_id, frame_id)  (2026-08-26)

ทบทวนเมื่อ: ทีม AI ยืนยันกติกาการตั้ง frame_id ; ถ้าเขาไม่รับประกันว่า unique
            ต้องเปลี่ยนไป dedup ด้วย (point_id, captured_at) แทน

## D-007 ยังไม่ partition ตาราง readings — ทำ BRIN ก่อน  (2026-08-26)
เลือก:      ตาราง readings ธรรมดา + BRIN บน captured_at + btree (point_id, captured_at DESC)
แทนที่จะ:   partition รายเดือนตั้งแต่แรกตามที่ D-002 เขียนไว้
เพราะ:      Postgres ไม่สร้าง partition ให้เอง — ถ้าไม่มีงานสร้างล่วงหน้า พอขึ้นเดือนใหม่
            INSERT จะ error ทันที = ข้อมูลหายตอนเที่ยงคืนวันที่ 1 บนเครื่องที่ไม่มีคนเฝ้า ;
            ยังไม่รู้อัตรายิงจริงจากทีม AI จึงยังไม่รู้ว่าคุ้มไหม ; แปลงทีหลังตอนตารางเล็กยังถูก
trade-off:  ถ้าปล่อยจนตารางโตมากค่อยแปลง ต้องมี downtime สั้น ๆ ตอน copy ข้อมูล ;
            การลบข้อมูลเก่าจะเป็น DELETE (ทำให้ตารางบวม ต้อง VACUUM) แทน DROP PARTITION ที่ทันที
ทบทวนเมื่อ: รู้อัตรายิงจริง หรือใกล้ production (พื้นที่บน SD เริ่มตึง) → ทำ T-009

## D-006 Postgres อยู่บน SD ไปก่อน + pg_dump cron  (2026-08-26)
เลือก:      เก็บ data ของ Postgres บน SD card ของ Pi + ตั้ง pg_dump cron ส่งออกไปเครื่องอื่น
แทนที่จะ:   ซื้อ NVMe HAT + SSD มาใส่ตั้งแต่ตอนนี้
เพราะ:      ยังเป็นช่วง dev ยังไม่มีข้อมูลจริงที่เสียไม่ได้ ; ความเสี่ยงหลักคือไฟดับกลางคัน
            ทำให้ DB corrupt (ไม่ใช่ SD สึก — write rate ต่ำมาก) ซึ่ง dump ที่อยู่นอกเครื่องกู้ได้
trade-off:  ไฟดับแล้ว corrupt = เสียข้อมูลตั้งแต่ dump ล่าสุดถึงตอนดับ ; ต้องไม่ลืมตั้ง cron จริง
            ไม่งั้นการตัดสินใจนี้กลายเป็นการยอมรับความเสี่ยงเปล่า ๆ
ทบทวนเมื่อ: ก่อนส่งมอบ/ใช้งานจริงในโรงงาน — ตอนนั้นควรอัปเกรดเป็น NVMe + UPS

## D-005 ใช้ MQTT LWT ประกาศเครื่องตาย ไม่พึ่งโค้ดตอนปิดตัวเอง  (2026-08-25)
เลือก:      LWT (Last Will and Testament) + topic `<prefix>/<device>/device_status` แบบ retained
แทนที่จะ:   ล้าง retained frame ใน SIGINT/SIGTERM handler ตอน process ปิด
เพราะ:      handler ตอนออกไม่ครอบคลุมสิ่งที่เกิดจริงกับ edge ในโรงงาน — ไฟดับ สายหลุด kill -9
            ล้วนไม่มีโอกาสรันโค้ด ; และพิสูจน์แล้วว่าบน Windows/Bun สัญญาณไม่ถึง JS เลย
            (exit 143 handler ไม่ทำงาน retained ค้างครบ 3) ; broker เท่านั้นที่ประกาศแทนได้
trade-off:  เพิ่มข้อกำหนดให้ทีม AI — edge ทุกตัวต้องตั้ง LWT เอง (OPEN-7 ใน contract/messages.ts)
            ถ้าเขาไม่ทำ เราจะแยก "ตาย" กับ "ยังไม่ถึงรอบส่ง" ไม่ออก ; retained frame ยังค้างอยู่
            ผู้อ่านต้องดู device_status ควบคู่เสมอ ไม่ใช่ดูแต่ค่า
ทบทวนเมื่อ: ทีม AI ยืนยันว่าตั้ง LWT ไม่ได้ → ต้องถอยไปใช้ heartbeat timeout ซึ่งช้ากว่าและพลาดง่ายกว่า
✅ ทดสอบบน Pi 5 (Linux) 2026-08-26: เส้นทาง **ปิดแบบสุภาพ (Ctrl+C) ทำงานจริง** → OFFLINE ครบ 3
   ซึ่งบน Windows ทดสอบไม่ได้เลยเพราะ signal ไปไม่ถึง JS — ยืนยันว่าโค้ด handler ถูกต้อง
   เส้นทาง **LWT (kill -9) ยืนยันบน Pi แล้ว**: เห็น ONLINE → ฆ่าดิบ → พลิกเป็น OFFLINE จริง
   (เทสรอบแรกสรุปไม่ได้เพราะ retained ค้างจากรอบก่อน ต้องคุมลำดับให้เห็น ONLINE ก่อนเสมอ)
